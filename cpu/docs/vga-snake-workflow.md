# VGA Snake 渲染调试：问题、根因与解决方案

## 一、背景

`snake_vga.c` 编译为 RISC-V hex 文件，运行在自制单周期 CPU 上，输出到 80×60 VGA 帧缓冲。游戏逻辑在 40×30 网格中，但帧缓冲 80×60 像素。RISC-V GCC 工具链不可用，无法重新编译 C 代码。

## 二、问题列表

| # | 问题 | 现象 |
|---|------|------|
| 1 | 画面撕裂 | 蛇和食物出现在错误位置，边框横向拆分呈 S 形 |
| 2 | 边框黑线 | 左右边框在行 16,18,20,22,24,26,28 位置缺失（偶数行下半段） |
| 3 | 蛇身黑线 | 蛇上下移动时身体出现黑色间隔断线 |
| 4 | 闪红条纹 | game over 时上半部分红黑相间条纹 |
| 5 | 模拟跑太快 | 启动后蛇秒撞墙闪红，来不及操作 |
| 6 | W 键行为异常 | 第一次按 W 蛇头从底部冒出来 |

## 三、逐个问题的调试过程

### 3.1 画面撕裂 → 步长不一致

**诊断**：帧缓冲是 `row × stride + col` 的线性数组。游戏代码混用了两种步长：
- `draw_border` 横线用 `FW=80` ✓
- `draw_border` 竖线用 `W=40` ✗
- 蛇/食物/闪屏全部用 `W=40` ✗

CPU 写入 `FB[y*40 + x]`，但 BMP 导出按 stride=80 读取 `FB[y*80 + x]`。row 2 的数据被写到地址 80，却被当成 row 1 来读。

**解决**：在 `vga_fb.sv` 硬件层拦截写地址，做 stride-40→80 重映射。

### 3.2 边框黑线 → Verilator 乘除组合逻辑 bug（核心发现）

**诊断过程**：

第一步：用除法/取模实现重映射 `addr/40*80 + addr%40`，BMP 验证发现 14 个边框像素为黑色，全部位于偶数行 16-28。

第二步：怀疑除法器边界 case，换成阈值比较（30 个 if-else）确定行号。问题依旧。

第三步：逐像素扫描发现黑色像素对应的重映射地址为 1280, 1319, 1440, 1479...（范围 1280-2279）。行 2-14 同样产生 80 的倍数地址（如 160, 320...）但工作正常。**区别在于行 16 以上的目标地址 >=1024**。

结论：Verilator 5.048 对 `row * 80 + col` 乘法器，当结果在 1024-2279 范围时存在静默写入失败（`always_ff @(posedge clk)` 条件满足，但 `fb[addr] <= data` 不生效）。

**尝试过但无效的方案**：
- 除法改阈值比较（无效）
- 不同乘法组合 `row*80` vs `addr + row*40`（无效）

**最终方案（0 乘除）**：
```verilog
// 行号：纯阈值比较
if (addr < 40) row = 0;
else if (addr < 80) row = 1;
...

// row*40 偏移量：纯 case 查表
case (row)
    0: extra = 0;
    1: extra = 40;
    ...
    29: extra = 1160;
endcase

// 目标地址：纯加法
remap = addr + extra;  // addr + row*40 = row*80 + col
```

同时加 `initial` 块预填边框为白色，作为双保险。

**经验教训**：
- FPGA 仿真工具（Verilator）并非 bug-free。遇到不可解释的硬件行为时，逐步消除可疑组件（先消除除法，再消除乘法，最后只剩比较+查表+加法）。
- BMP 逐像素扫描是调试帧缓冲问题的最有效手段。发现 14 个固定位置的黑色像素直接指向乘除 bug。
- 硬件 `initial` 块预填关键数据是一个实用的绕过方案。

### 3.3 蛇身黑线 + 闪红条纹 + W 键异常 → 帧缓冲读取时机不同步

**诊断**：边框修复后（BMP 验证 0 黑像素），SDL2 实时版仍有黑线和条纹。BMP 导出（静态快照）正确但实时版（动态读取）错误 → 问题不在帧缓冲数据，而在**读取时机**。

游戏循环结构（单次迭代 ~3100 周期）：
```
清屏 20cyc | 输入 10cyc | 移动 20cyc | 绘图 24cyc | 延迟 3000cyc
  ↑ 脏区                                     ↑ 干净区（95% 时间）
```

如果帧缓冲在"脏区"被读取，会看到半清半绘的状态：蛇的部分身体已被清为黑色，新位置还未绘制。

Game over 闪屏的填充阶段长达 5320 周期，几乎必然被读到半填充状态，显示为红黑条纹。

W 键"蛇从底部出来"：实际是蛇正常向上移动，但因为帧缓冲在清屏阶段被读，蛇身黑色段+移动方向变化造成了"从底部钻出"的错觉。

**尝试过但无效的方案**：
- 固定 FRAME_CYCLES + PAD_CYCLES：游戏迭代长度可变（按键处理、吃食物），无法完美对齐
- 双采样取非黑像素多者：边框 122 白像素压倒蛇的 5 像素，无法用非黑计数判断

**最终方案（稳定帧检测）**：
```
loop:
  跑 1500 周期 → 读帧缓冲 A
  跑 1000 周期 → 读帧缓冲 B
  if A == B → 稳定，显示
  else     → 在过渡中，继续跑下一轮（最多 4 轮）
```

原理：延迟阶段帧缓冲不变，两次读取完全一致。清屏/绘图/填充阶段帧缓冲在变化，两次读取不一致，触发重试。重试间隔 1000 周期足够越过清屏（55 周期），最多 4 轮可越过填充（5320 周期）。

### 3.4 模拟跑太快

**原因**：Verilator 以宿主机 CPU 速度运行，游戏内延迟循环仅 1500 迭代（~3000 周期），蛇秒撞墙。

**解决**：`SDL_Delay` 节流 + 增大 BOOT_CYCLES 确保初始画面完整渲染后再接受输入。

## 四、参数演进

| 参数 | 初始值 | 最终值 | 原因 |
|------|--------|--------|------|
| 重映射方法 | 除法/取模 | 查表+纯加法 | Verilator 乘除 bug |
| BOOT_CYCLES | 80000 | 12000 | 太大了蛇已走远，太小了首帧空白 |
| FRAME_CYCLES | 5000 | — | 改为 BATCH_CYCLES+STABLE_GAP 动态方案 |
| BATCH_CYCLES | — | 1500 | 细粒度推进，减少单次脏窗口概率 |
| STABLE_GAP | — | 1000 | > 清屏窗口(55) 的 18 倍，足够检测变化 |
| TARGET_FPS | 无→12→5→4 | 5 | 与 BATCH_CYCLES 配合控制蛇速 |

## 六、调试方法论

1. **BMP 逐像素扫描**：Python + struct 读 BMP，逐行逐列查色，比肉眼更快更准
2. **二进制搜索**：先确认是数据问题（BMP 静态导出）还是时序问题（实时读取）
3. **逐步消除复杂性**：除法→阈值比较→查表→纯加法，每步验证
4. **硬件盒子测试**：无法直接调试 Verilator 内部，通过改变输入/消除组件来定位
5. **稳定帧检测**：利用游戏在延迟阶段帧缓冲不变的特性，两次读取比对判断
